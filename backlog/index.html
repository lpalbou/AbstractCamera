    Open items¶

    ID Item Notes
    0001 Size-aware rolling ring The pre-capture ring is seconds-based; at 1080p/q85 a 10s ring is ~66-130MB (disclosed in docs). A byte-budgeted ring would bound memory explicitly.
    0002 Bulb exposures Both validated PTP bodies refuse remote Bulb writes; the bulb action toggle on Sony is accepted but unvalidated. Needs a hardware session dedicated to bulb choreography + timing ownership.
    0004 Webcam duration bursts Count mode shipped (validated); round(hold_s * fps) duration bursts are trivial if a host wants the Sony-style knob on webcams.
    0005 Linux/Windows webcam drivers The webcam driver is macOS/AVFoundation only (honest available()=False elsewhere); v4l2 and DirectShow enumeration are future families of work. Absorbed by 0022 (2026-09-29).
    0006 Canon EOS family eosremoterelease press choreography, EOS event vocabulary; one adapter file + a select_adapter match when a body is available to measure.
    0008 Sony trigger-drop root cause The A7R IV intermittently accepts trigger_capture and never fires, even in Manual focus (observed 2026-07-12; the expectation watch reports each drop honestly). Root cause unknown — candidate: internal busy states while digesting settings/card writes. Needs a dedicated hardware session correlating drops with preceding operations.
    0009 Hub-level "fire all" choreography The hub pilots cameras independently; a synchronized multi-camera trigger (single wall-clock deadline across bodies) would serve rigs. Needs per-family latency compensation to be meaningful.
    0011 Core-side camera facade + /v1/camera/* server routes Asked to the core seat at commons c3135: CameraCapability protocol, _CameraFacade, register_camera_backend, "camera" in status(), core.camera property, extension endpoints (/v1/audio/music precedent). Camera-side is ready (ADR 0012); core owns the merge.
    0018 Artifact-branch size cap + residual P2s _attach_capture_payload reads whole files into RAM; the 64MB cap guards only the inline branch — the artifact_store branch hands unbounded bytes (600s MP4 = hundreds of MB) to byte-in-memory stores (abstractcore_plugin.py:377-391). Fix: cap the artifact branch too, name the file path in the error. Also P2s from the 2026-07-21 passes: connect-timeout zombie thread (camera_manager.py worker assign-after-wait), sim claim-registry gap (double-open succeeds in sim where PTP wedges — add exclusive-claim so lifecycle races fail in CI), error texts routing agents to surfaces they cannot reach (sync_store hints in tool errors), hub default-connect skipping already-claimed devices (behavior change; docstring warns today).
    0020 DWARF astro choreography through service/tools (proposed — PARKED until ~Aug 4, operator ruling c4089: "Forget about the Dwarf for the next 2 weeks") The flagship physical-world demo: an agent slews the telescope to a target, calibrates, and runs a capture sequence. Blocked on two lanes (adversarial roadmap 2026-07-21): the DWARF control lane is implemented from the published spec but not hardware-validated (scripts/validate_dwarf.py is the moment of truth; only the card/media half has real-hardware validation), and the service/tool surface exposes neither request_action (GOTO lives only on CameraManager) nor start_interval_sequence. Order: hardware session → expose actions+sequences through service/tools → choreography as a flow/skill, never package code.
    0021 Config-channel reach for deployment defaults (env adversary P2, 2026-07-21) The env-classification adversary confirmed ZERO behavior env vars (nothing to migrate under dm#177), but named two deployment-var reach gaps worth closing so "configurable on the gateway/console" holds fully: (a) capture-root console reach — owner/console config (_owner_cfg("camera_capture_root")) is read only in the capability plugin lane; the tool lane (get_shared_service() in abstractcore_tools) and CLI read env-or-default only, and the process-shared hub is last-caller-wins, so a tool-opened camera can keep the env layout after console config lands. Fix: resolve owner/console config at shared-service resolution, not only in the capability constructor. (b) DWARF hosts config surface — ABSTRACTCAMERA_DWARF_HOSTS/_CLIENT_ID have NO config surface at all (every production path constructs DwarfDriver() bare; env is the sole control); carry them through the owner-config channel at DWARF unpark (config-wins over env). Both are deployment-class (data dir / device addresses), env-legitimate today; these are polish toward the ruling's second half, not behavior migrations. P3 also: _CONFIG_HINT should lead with the config key and demote the env spelling.
    0022 AbstractCamera in every AbstractCore install setting (planned) Operator ruling 2026-09-29: camera in light, apple and gpu. Not light work: the base installs wheel-only everywhere, but only macOS gets a working camera (no Linux/Windows webcam driver; headless Linux cannot import the GUI opencv-python without libGL). Plan, per-OS evidence and acceptance criteria: planned/0022_camera_in_every_abstractcore_setting.md.
